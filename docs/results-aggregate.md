# KAFKA RESULTS aggregate contract

`results/results.json` is the canonical cross-repository view for KAFKA RESULTS. It is generated by `scripts/aggregate_results.py`; `results/RESULTS.md` is a deterministic human-readable projection of that JSON and is not a second source of truth.

## Inputs

The aggregator consumes the latest successful evidence artifacts produced by the six domain workflows:

- `kafka-results-code-quality` → `results/code-quality/*.json`
- `kafka-results-data-quality` → `results/data-quality/*.json`
- `kafka-results-reliability` → `results/reliability/*.json`
- `kafka-results-automation` → `results/automation/*.json`
- `kafka-results-adoption` → `results/adoption/*.json`
- `kafka-results-business` → `results/business/*.json`

The aggregate workflow downloads those artifacts instead of reimplementing or rerunning domain measurement logic. Each input must have the exact domain `schema_version` expected by the aggregator. `--require-all` fails closed when any domain artifact is absent.

## Canonical identity and provenance

Each repository/category pair receives a deterministic `canonical_result_id` derived from:

```text
category + repository + domain schema version
```

The complete domain payload is hashed with canonical JSON and recorded as `input_sha256`. If two files resolve to the same canonical ID but their hashes differ, aggregation fails rather than silently choosing one. URL-shaped evidence fields are copied into `evidence_urls`; malformed URL evidence fails validation.

The aggregate does not copy the whole domain payload into `results.json`. The source path, exact input SHA-256, schema version, repository and evidence URLs are retained so the aggregate can be traced to the downloaded domain evidence without duplicating the domain record as a second canonical dataset.

## Unknown, N/A and zero

`0` is preserved only when a domain collector explicitly measured zero. `null`, `unknown`, `not_instrumented` and `not_available` remain distinct. The aggregator does not create a composite score across metrics with different units or denominators.

A summary KPI is populated only when the source domain marks the underlying metric as measured. Examples:

- workflow first-attempt success rate is recomputed from recorded first-attempt numerators/denominators;
- scheduled automated starts count only recorded `schedule` workflow events;
- stars/forks are not converted into observed users;
- price × count is not converted into revenue;
- CI failures are not converted into reproducible product bugs.

## Views

`results.json` contains deterministic views by repository, category, trend and period. Period coverage is evidence-aware: a 30-day source window can be marked observed, while an unsupported `today`, `7d` or all-time view remains `not_available`. Business/service declarations are indexed by their repository-owned declaration paths rather than inferred product names.

## Daily snapshots and corrections

The snapshot date is derived from the newest valid timestamp contained in the inputs. The first aggregate for a date is written as:

```text
results/snapshots/YYYY-MM-DD.json
```

A byte-equivalent rerun reuses the same snapshot. If the same date is corrected with different evidence, the original file is not overwritten; the new revision is written as `YYYY-MM-DD-r2.json`, then `-r3`, and so on.

## CI gate

`.github/workflows/results-aggregate.yml` verifies:

1. aggregator unit tests;
2. existence of a successful main artifact for all six domain workflows;
3. exact domain schemas and valid evidence URLs;
4. non-empty backfill;
5. canonical ID uniqueness and SHA-256 syntax;
6. `results.json` / daily snapshot equality;
7. generated Markdown and JSON schema presence;
8. a clean checkout after generated results are removed.

The resulting `kafka-results-aggregate` artifact is retained for 30 days. It contains only the canonical aggregate JSON, generated Markdown, schema and dated snapshot; domain artifacts remain owned by their respective workflows.
