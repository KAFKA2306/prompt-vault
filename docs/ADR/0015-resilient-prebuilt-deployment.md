# ADR 0015: プリビルド成果物のリポジトリ管理と弾力的な配信構成

## ステータス
承認済み (Accepted)

## コンテキスト
プロジェクトは GitHub Pages と Cloudflare Pages の両方に配信されているが、それぞれのビルド環境（Python バージョン、Pillow 等の外部依存の有無）に差異があり、一貫した WebP 最適化と安定した配信を維持することが困難であった。

特に Cloudflare Pages において、ビルド環境の不一致により `dist/` ディレクトリが生成されず、配信が停止するリスクが顕在化した。

## 決定事項
以下の 3 点をアーキテクチャの基本原則として決定した。

1. **成果物（dist/）のリポジトリ管理**:
   - ビルド済みの `dist/` ディレクトリを `.gitignore` から除外し、バージョン管理対象とする。
   - これにより、手元の確実な環境で生成された「WebP 最適化済み成果物」をプロジェクトの正典 (Source of Truth) とする。

2. **弾力的なビルドスクリプト (build.py)**:
   - `build.py` は Pillow 等の外部依存の有無を動的に検知する。
   - Pillow がある環境では WebP 最適化を行い、ない環境では自動的に PNG コピーへフォールバックする。
   - これにより、どのような CI/CD 環境でも「ビルド自体は必ず成功する」状態を保証する。

3. **ビルド情報の刻印 (Observability)**:
   - ビルド時に最新のコミットハッシュを `index.html` のコメントとして埋め込む。
   - 本番環境から物理的なハッシュを確認可能にすることで、配信内容の再現性と透過性を確保する。

## 理由
- **安定性の最大化**: サーバー側でのビルド工程をバイパスすることで、「ビルド失敗によるサイト停止」のリスクを物理的にゼロにする。
- **再現性の 100% 保証**: ローカルで検証された成果物をそのまま配信するため、環境依存のバグを排除できる。
- **管理コストの削減 (Zero-Fat)**: Cloudflare への API プッシュやシークレット管理、複雑な依存関係定義 (`requirements.txt` 等) を不要にする。

## デメリットと対策
- **リポジトリサイズの増加**: 画像アセットを含む `dist/` が含まれるため、リポジトリサイズが増加する。
  - **対策**: WebP 化により総サイズを 30MB 程度に抑制しており、現在の規模では Git の許容範囲内である。
- **同期漏れのリスク**: 開発者が `build.py` を実行し忘れてコミットする可能性がある。
  - **対策**: GitHub Actions 等で「ビルド結果がコミット内容と一致するか」のバリデーションを検討する。

## 証拠 (Verification)
- `index.html` 末尾の `<!-- Build: [commit_hash] -->` の存在を確認。
- Cloudflare Pages / GitHub Pages の両方で 200 OK と画像が表示されていることを確認。
