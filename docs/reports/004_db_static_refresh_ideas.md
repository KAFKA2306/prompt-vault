# 004 DB And Static Refresh Ideas

> 最終決定は [ADR](../ADR/README.md) を見る。このメモは、刷新の候補を単純明快に整理するための記録。

## 結論

今の `db/prompts.json` と `static/app.js` は、壊さずに伸ばせる。
ただし、再利用性をもっと上げたいなら、`graph` として考えるのが一番わかりやすい。

## いまの前提

- `db/prompts.json` はまだ 1 つの静的 DB として扱う
- `blocks` は部品
- `templates` は組み立てレシピ
- `uses`、`related`、`variant_of`、`aliases` を関係の補助として使う
- `static/app.js` は表示だけでなく、関係をたどる役も持つ
- `build.py` は参照の整合性を止める

## 刷新する場所

### 1. `db/*`

- 同じ意味の部品を増やさない
- 似た部品は `variant_of` でつなぐ
- 探しやすさは `aliases` で吸収する
- 横断のつながりは `related` で表す
- 再利用先は `uses` で明示する

### 2. `static/*`

- 画面はギャラリー中心のままにする
- モーダルは全文コピーの入り口として保つ
- `related` と `uses` をクリックして辿れるようにする
- おすすめは「よく使う順」にする
- 画像がないノードでも、関連先の実例を拾って見せる

## すすめる順

1. 参照検証を壊さず続ける
2. 関係キーを少しずつ増やす
3. おすすめ表示を強くする
4. 重複部品をまとめる
5. それでも足りなければファイル分割を考える

## やらないこと

- いきなり Graph DB に移さない
- いきなり SQLite に置き換えない
- いきなり複雑なダッシュボードにしない
- 既存のギャラリー・モーダル・コピーの流れを壊さない

## 学び

- 用語を graph 寄りにすると、関係を考えやすくなる
- ただし、用語だけ変えても構造が変わらないと効果は小さい
- 最小の刷新は、キーの追加と参照の明示で十分効く
